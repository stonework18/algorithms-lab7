## Контрольные вопросы

# Ответы на вопросы

## 1. Какова сложность быстрой сортировки в лучшем, среднем и худшем случае?

Лучший -  **O(n log n)**. Опора каждый раз делит массив примерно пополам 
Средний - **O(n log n)**. Случайные данные, «нормальные» опоры
Худший - **O(n²)**. Опора каждый раз оказывается минимумом или максимумом

## 2. Когда возникает худший случай для быстрой сортировки?

Когда разбиение получается **максимально несбалансированным**: на каждом уровне опора — min или max, и одна из веток пустая, другая — размером `n-1`. Тогда глубина рекурсии `n`, а суммарная работа `n + (n-1) + ... + 1 = O(n²)`.

## 3. Как можно улучшить быструю сортировку для защиты от худшего случая?

1. **Insertion sort на маленьких подмассивах** (≤ 16) — не про худший случай, но снижает константы.
2. **Итеративная реализация с явным стеком** — защита от stack overflow при плохой глубине.

## 4. Какова сложность сортировки слиянием? Почему она всегда O(n log n)?

**Всегда O(n log n)** — лучший, средний, худший.

Почему: рекуррентное соотношение
```
T(n) = 2·T(n/2) + O(n)
```
- **деление** пополам — `O(1)`;
- **два рекурсивных вызова** по `n/2`;
- **слияние** двух половин — строго `O(n)`, потому что на каждый элемент выполняется не больше одной операции сравнения/копирования.

На каждом уровне суммарно `O(n)`. Итого `O(n log n)` **при любых входных данных** — никакой зависимости от удачности опоры.

## 5. Какие преимущества и недостатки имеет сортировка слиянием перед быстрой?

**Плюсы merge sort:**
- **гарантированное** O(n log n) — нет худшего случая;
- **устойчивый** (при `<=` в слиянии, как у тебя);
- **предсказуемое** время — важно для real-time;
- хорошо работает на **связных списках** (не нужен random access) и при **внешней сортировке** (файлы больше RAM);
- легко **распараллеливается** — половины независимы.

**Минусы merge sort:**
- требует **O(n) дополнительной памяти**;
- **хуже локальность кеша** — читает/пишет два буфера;
- на массивах **медленнее** quicksort из-за копирований;

## 6. Как работает пирамидальная сортировка? Какова её сложность?

**Две фазы:**

1. **Построение max-кучи** из неотсортированного массива. Идём от последнего внутреннего узла (`n/2 - 1`) к корню, вызываем `heapify`. Суммарно **O(n)** — хотя каждый `heapify` до `O(log n)`, сумма по всем узлам сходится к линейной (высокие узлы мало, низкие много).
2. **Извлечение максимума**: `swap(arr[0], arr[i])` — максимум уезжает в конец, `heapify(arr, i, 0)` восстанавливает кучу на `i` элементах. `n-1` раз по `O(log n)` → **O(n log n)**.

**Итог:** `O(n log n)` во всех случаях, доп. память O(1).

## 7. Какая из трёх сортировок устойчивая? Почему?

**Только merge sort.** Устойчивость обеспечивается условием `L[i] <= R[j]` в `merge`: при равенстве берём из **левой** половины, поэтому равные элементы сохраняют относительный порядок.

## 8. Какая из трёх сортировок требует дополнительной памяти? Сколько?

**Merge sort**. **O(n)** — буферы `L` и `R` (можно `O(n)` общий буфер на всю сортировку) 
**Quick sort**. **O(log n)** в среднем — стек рекурсии; **O(n)** в худшем 
**Heap sort**. **O(1)** — in-place, если `heapify` итеративный; в твоём рекурсивном — `O(log n)` на стек 

## 9. Какая из трёх сортировок лучше работает на почти отсортированных данных?

- **Merge sort** — стабильно O(n log n), не зависит от входных данных. Хорошо, но не использует «почти отсортированность».
- **Quick sort** — O(n²) на отсортированном.
- **Heap sort** — всегда O(n log n), «почти отсортированность» никак не помогает.

## 10. Зачем в пирамидальной сортировке сначала строится куча?

Куча (max-heap) — это структура, где **корень всегда максимальный элемент**, и это свойство поддерживается за O(log n) после изменения. Без построения кучи `arr[0]` не был бы максимумом, и алгоритм не смог бы:

1. **Извлекать максимум за O(1)** — просто `arr[0]`.
2. **Ставить максимум в конец** — `swap(arr[0], arr[i])`.
3. **Восстанавливать кучу за O(log n)** — `heapify` на оставшейся части.

## 11. Что такое «разделяй и властвуй»? Как он применяется в быстрой сортировке и сортировке слиянием?

**Парадигма:** разбить задачу на подзадачи того же типа, решить их рекурсивно, объединить результаты.

**Quick sort:**
1. **Разделяй:** `partition` делит массив на `< pivot` и `≥ pivot` вокруг опоры.
2. **Властвуй:** рекурсивно сортируем обе части.
3. **Объединяй:** **ничего делать не надо** — после разбиения всё уже на своих местах (опора между ветками). Это уникальная черта quicksort.

**Merge sort:**
1. **Разделяй:** `mid = (left + right) / 2` — просто делим пополам (без сравнений!).
2. **Властвуй:** рекурсивно сортируем обе половины.
3. **Объединяй:** `merge` — **сливаем две отсортированные половины за O(n)**. Это ключевая часть, где вся работа.

Разница в акцентах: **quick sort работает на этапе «разделяй»** (partition трудоёмкий, объединение тривиально), **merge sort — на этапе «объединяй»** (разделение тривиально, merge трудоёмкий).

## 12. Можно ли реализовать быструю сортировку итеративно (без рекурсии)?

**Да.** Рекурсия — просто синтаксический сахар над стеком; её можно заменить **явным стеком**:

```cpp
void quickSortIter(int arr[], int n) {
    stack<pair<int,int>> st;
    st.push({0, n - 1});

    while (!st.empty()) {
        auto [low, high] = st.top(); st.pop();
        if (low >= high) continue;

        if (high - low > 16) medianOfThree(arr, low, high);
        int pi = partition(arr, low, high);

        // пушим обе ветки — порядок не важен
        st.push({low, pi - 1});
        st.push({pi + 1, high});
    }
}
```

## 13. Почему быстрая сортировка обычно быстрее сортировки слиянием на практике?

У quicksort лучше **константы**:

1. **In-place** — не нужны O(n) дополнительных аллокаций. В merge sort на каждом шаге `new/delete` — это дорого.
2. **Лучшая cache locality** — quicksort работает с последовательным куском памяти, прыжки локальные. Merge sort прыгает между исходным `arr` и буферами `L`, `R`.
3. **Меньше копирований** — quicksort только swaps, merge sort копирует все элементы `n·log n` раз.
4. **Меньше записи в память** — merge sort делает `n·log₂n` записей, quicksort — в среднем ~`n·log₂n / 6` перестановок.

## 14. Когда выгодно использовать пирамидальную сортировку?

- **Жёсткие требования к памяти** — O(1) или O(log n) дополнительной; альтернативы merge (нужно O(n)) нет.
- **Гарантия O(n log n)** без сложностей introsort — предсказуемость важнее скорости.
- **Задача «k наименьших/наибольших»** — построить кучу за O(n), затем k раз извлечь за O(k log n). Частичная сортировка — быстро.
- **Priority queue** — куча это и есть структура данных приоритетной очереди; heapSort — «побочный продукт».

## 15. Какой алгоритм сортировки вы бы выбрали для встроенных систем с ограниченной памятью?

introsort — оптимальный выбор для embedded: он даёт лучшее из quicksort (скорость, in-place) и heapsort (гарантию O(n log n)), используя O(log n) памяти. При запрете рекурсии или критичности даже log n стека — heapsort.
